# OpenVisTool 数据集设计总览

OpenVisTool 是一个面向视觉工具调用蒸馏的多领域轨迹数据集。它的目标不是只收集“答案正确”的视觉问答样本，而是收集模型在解决视觉任务时主动调用工具、获取证据、修正判断并最终完成任务的过程。数据集关注两个核心问题：

- 任务是否真的需要视觉工具，而不是仅靠文本先验或粗略看图就能完成。
- 轨迹中的工具输出是否真的提升了解题能力，而不是无意义地模仿工具调用形式。

主数据集约 42K 条轨迹，覆盖 Chart、GUI Grounding、Table、Visual Search 和 Web-to-HTML 五个互补领域。

## 涉及领域

| 领域 | 任务目标 | 视觉瓶颈 | 主要来源/产物规模 |
| --- | --- | --- | --- |
| Chart | 理解图表、读取坐标轴/图例/系列颜色、比较或计算数值 | 小字号、密集图例、颜色系列、轴线对齐、数值估算 | ChartVerse，约 14K |
| GUI Grounding | 在桌面或应用截图中定位目标控件并给出点击位置 | 高分辨率截图、目标控件小、相邻控件密集、坐标精度要求高 | OS-Atlas、Ubuntu、UGround，约 11K |
| Table | 阅读表格图像，定位行列交叉单元并做比较/汇总 | 行列对齐、细小数字、跨列/跨行引用、低对比度表格 | TABLET-Small、CoSyn-400K，约 5K |
| Visual Search | 在复杂图像中寻找、计数或验证目标物体/属性 | 小目标、遮挡、背景杂乱、颜色/空间关系判断 | Vero-600k、DeepEyesV2-RL，约 2K |
| Web-to-HTML / VinciCoder | 根据网页截图生成视觉一致的 HTML，并通过渲染闭环检查 | 布局复现、颜色/间距/字体近似、渲染后视觉差异修正 | VinciCoder，约 11K |

这些领域的选择原则是互补性：不同任务暴露不同的视觉工具需求。Chart 和 Table 强调精细读数与结构对齐；GUI Grounding 强调局部放大与坐标映射；Visual Search 强调在大图中主动搜索证据；Web-to-HTML 强调生成结果的可视化自检。

## 工具大类

OpenVisTool 采用统一的视觉工具集，但不同领域会自然偏向不同工具。宏观上可以按工具目的划分为以下几类：

| 工具类别 | 代表工具 | 设计目的 | 典型适用领域 |
| --- | --- | --- | --- |
| 视野裁剪与坐标映射 | `crop`, `locate_in_crop`, `rotate`, `flip` | 把原图中难以直接观察的区域放大，或把局部坐标映射回原图 | GUI Grounding、Chart、Table、Visual Search |
| 标注与对齐辅助 | `draw_bbox`, `draw_line`, `draw_circle` | 用可视化标记帮助模型追踪目标、对齐行列/坐标轴、确认候选区域 | Chart、Table、Visual Search、GUI Grounding |
| 图像可读性增强 | `enhance_contrast`, `adjust_brightness`, `grayscale`, `detect_edges` | 提升低对比度、暗光、细线条或小文字场景下的可读性 | Table、Chart、Visual Search |
| 颜色与区域分析 | `in_range_color`, `sample_color`, `color_segments`, `color_clusters` | 分离特定颜色区域，识别图例系列、按钮颜色、目标物体颜色或网页配色 | Chart、GUI Grounding、Visual Search、Web-to-HTML |
| 形状与结构检测 | `connected_components`, `find_contours`, `hough_lines`, `hough_circles`, `template_match` | 辅助识别连通区域、边界、直线/圆形结构或重复模板 | Table、Chart、GUI Grounding、Visual Search |
| 生成结果验证 | `render_html` | 将生成的 HTML 渲染成截图，形成“生成-观察-修正”的闭环 | Web-to-HTML / VinciCoder |
| 动作表达与计算辅助 | `computer_use`, `exec`, file tools | 表达最终 GUI 点击动作，或把复杂计算/代码草稿交给确定性工具处理 | GUI Grounding、Chart、Table、Web-to-HTML |

工具设计的核心思想是让模型把“看不清、对不准、算不稳、生成后不确定”的部分交给外部工具，而不是在原始视觉输入上直接猜测。

## 轨迹构造管线

OpenVisTool 的轨迹构造可以按目的分成六个阶段。

### 1. 收集多领域任务

先从多个视觉任务源中收集问题、图像和答案。领域覆盖的目标不是追求单一 benchmark 的规模，而是让工具调用学习到多种视觉证据获取方式：放大、标注、颜色分离、结构对齐、渲染验证、最终动作表达等。

### 2. 过滤不需要工具的样本

对每个候选样本先评估基础模型在无工具条件下的表现。若样本不调用工具也能稳定解决，则对视觉工具学习价值较低，会被剔除。对部分来源，还会选择中等难度区间，避免保留过易或基本不可解的样本。

这一阶段的目的不是筛出“难题”本身，而是筛出“有机会通过工具获得额外证据”的题。

### 3. 教师模型生成工具轨迹

对保留下来的样本，使用强教师模型在统一工具集下进行多轮解题。每条轨迹记录模型如何思考、何时调用工具、工具返回了什么观察结果、模型如何根据新证据继续推理，直到生成最终答案、点击动作或 HTML。

轨迹的价值在于展示证据获取过程，而不是只展示最终回答。不同领域会用不同的任务指令引导工具使用，但工具接口保持统一。

### 4. 检查最终结果正确性

工具轨迹必须先通过最终结果检查。不同领域采用适合自身输出形式的检查方式：结构化答案可以用规则匹配，开放式回答可以用 judge，HTML 生成则需要先渲染再进行视觉比较。除此之外，还会剔除明显不合格的工具调用轨迹，例如缺少必要观察、路径不可复现或最终动作格式不合法。

这一阶段保证轨迹至少完成了任务。

### 5. 评估工具是否真的带来增益

仅正确还不够，因为教师可能在不需要工具的情况下也能答对。OpenVisTool 进一步评估工具输出是否真正有用：把教师轨迹中的工具观察提供给基础模型，再比较它相对无工具解题时的表现是否提升。

只有当工具观察带来足够正向增益时，样本才被认为是“工具有用”的轨迹。

## 数据变体

为了分析不同筛选标准的作用，OpenVisTool 同时保留多个变体：

| 变体 | 保留标准 | 用途 |
| --- | --- | --- |
| OpenVisTool | 正确性通过且工具增益通过 | 主数据集，强调正确且工具真正有用 |
| OpenVisTool_acc_only | 只要求最终答案正确 | 分析仅靠正确性过滤是否足够 |
| OpenVisTool_toolgain_only | 只要求工具增益通过 | 分析工具证据有用但最终轨迹未必可靠的影响 |
| OpenVisTool_notool | 相同问题上的无工具轨迹 | 对比“工具调用监督”和“纯推理监督”的差异 |

主数据集的设计假设是：高质量视觉工具调用数据应同时满足“完成任务”和“工具贡献证据”两个条件。正确性过滤保证监督目标可靠，工具增益过滤保证模型学到的不是表面化工具调用，而是工具辅助视觉推理的有效模式。
