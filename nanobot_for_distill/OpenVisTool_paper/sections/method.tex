\method synthesizes visual tool-use trajectories in four stages: query
collection and difficulty filtering (\S\ref{sec:queries}), the unified visual
toolset (\S\ref{sec:toolset}), teacher trajectory distillation
(\S\ref{sec:rollout}), and double rejection sampling
(\S\ref{sec:filtering}). We then convert the surviving trajectories to SFT
samples (\S\ref{sec:sft}).

\paragraph{Difficulty filtering.}
A query whose answer a base model already produces by text-only reasoning
teaches nothing about tool use. We score each query with a base model
(\TODO{Qwen3.5-9B}) using no-tool average accuracy over $k$ samples
($\text{avg}@k$) and discard queries that are too easy. \TODO{For sources with
abundant easy examples (\eg CoSyn-400K) we additionally restrict to a
difficulty band $\text{avg}@k \in [0.25, 0.75]$ to avoid both trivial and
unsolvable queries.}

\subsection{A Unified Visual Toolset}
\label{sec:toolset}

All domains share one heterogeneous toolset; each tool targets a distinct
perceptual bottleneck.
\begin{itemize}
  \item \texttt{crop} / \texttt{zoom} --- recover fine detail lost at the
  input resolution (visual search, GUI grounding, small chart text).
  \item \texttt{draw\_bbox} --- mark and re-attend to a located region.
  \item \texttt{in\_range\_color} --- isolate elements by color
  (chart series, highlighted UI elements).
  \item \texttt{render\_html} --- render generated HTML/code to a screenshot
  for visual self-verification (Web-to-HTML).
  \item \TODO{\texttt{computer\_use}, \texttt{enhance}, \texttt{transform},
  \texttt{feature}, and other tools---list the final enabled set.}
\end{itemize}
Tool schemas are extracted automatically from the tool implementations, and
files a tool produces are written to the trajectory's workspace with
relative paths so that exported trajectories are host-independent.

\subsection{Double Rejection Sampling}
\label{sec:filtering}

A distilled trajectory is kept only if it passes \emph{both} of the following.

\paragraph{(i) Answer correctness.}
We verify the teacher's final answer with one of three backends matched to the
domain: \emph{rule}-based matching (generic / point / bounding-box modes) for
grounding and structured answers, an \emph{LLM judge} for free-form answers,
and a \emph{render-based VLM judge} for Web-to-HTML (the generated code is
rendered to a screenshot and scored by a VLM). We additionally apply tool-call
sanity heuristics (\eg rejecting absolute host paths or missing images).

\paragraph{(ii) Tool gain.}
Correctness alone does not establish that the tool calls mattered. We define
the \toolgain of a trajectory as
\begin{equation}
  \Delta = \text{avg}@k_{\text{with-tool}} - \text{avg}@k_{\text{no-tool}},
  \label{eq:toolgain}
\end{equation}
where $\text{avg}@k_{\text{no-tool}}$ is the base model's accuracy on the query
with no tools, and $\text{avg}@k_{\text{with-tool}}$ is its accuracy when the
teacher's tool outputs are prepended to its context. A trajectory is retained
only when $\Delta$ exceeds a threshold $\tau$ (\TODO{default $0.1$}),
\ie\ seeing the tool outputs causally improves the base model. The final
\dataset is the intersection of the correctness-passing and tool-gain-passing
sets.

\paragraph{Ablation variants.}
To isolate the effect of each criterion we build three corpora: correctness
only, \toolgain only, and the intersection (the main \dataset). We compare
all three in \S\ref{sec:experiments}.
