\begin{abstract}
Visual tool-use distillation should teach models how to acquire evidence, not merely how to produce correct final answers. We present \method, a multi-domain trajectory dataset and synthesis recipe for visual tool use. \dataset contains 42K trajectories across Chart, GUI Grounding, Table, Visual Search, and Web-to-HTML tasks, covering complementary visual bottlenecks such as small text, dense layouts, coordinate precision, object search, color or structure analysis, and render-based verification. The key design principle is that a retained trajectory must satisfy two conditions: the task should benefit from tools, and the recorded tool outputs should actually improve solving the task. To enforce this, our pipeline first removes examples that are easily solved without tools, then distills teacher tool-use trajectories, checks final-answer correctness, and filters for \toolgain by measuring whether the teacher's tool observations improve a base model's performance. Fine-tuning on \dataset improves all five domains across four backbones, with average gains of 8.9--13.2 points. Ablations show that correctness and \toolgain filtering are complementary, and comparison with no-tool trajectory SFT shows that tool-use supervision is especially beneficial for evidence-acquisition tasks such as Visual Search and Table.
\end{abstract}

\section{Introduction}
\label{sec:introduction}

Many visual tasks are difficult not because the reasoning step is abstract, but because the relevant evidence is hard to observe in the original input. A chart may require reading small axis labels and matching a color series to a legend; a table question may require aligning a row and column across a low-contrast grid; a GUI grounding task may require locating a tiny control in a high-resolution screenshot; a visual-search query may require checking small or occluded objects in a cluttered scene; and Web-to-HTML generation requires rendering the generated code to inspect whether the layout, spacing, and colors actually match the reference. These cases expose a common need: the model should actively inspect, transform, mark, or verify the visual input instead of answering from a single static image.

This motivates visual tool-use distillation. A tool-using trajectory can show the model how to crop a small region, map local coordinates back to the original screenshot, draw alignment guides, isolate a color range, enhance a low-contrast area, render generated HTML, or express a final GUI action. The value of such data lies in the evidence-acquisition process: the trajectory records what the model chose to inspect, what the tool returned, and how the new observation changed the subsequent reasoning. A dataset that only records final answers misses this process, while a dataset that records arbitrary tool calls risks teaching the model to imitate tool-use syntax without learning when tools are useful.

We argue that high-quality visual tool-use data must answer two questions. First, does the task actually require or benefit from tools, rather than being solvable from text priors or a coarse view of the image? Second, within a successful trajectory, do the tool outputs genuinely improve the model's ability to solve the task, rather than serving as decorative or redundant actions? Final-answer correctness alone cannot answer either question. A teacher can produce the right answer even if the tool calls were unnecessary, and a plausible-looking tool call can appear in a trajectory whose final answer is wrong. Tool-use distillation therefore needs to filter both the tasks and the trajectories.

We introduce \method, an open recipe for constructing such data. The resulting \dataset contains 42K trajectories spanning five complementary domains: Chart, GUI Grounding, Table, Visual Search, and Web-to-HTML. These domains are selected for their different visual bottlenecks and tool demands. Chart and Table emphasize fine-grained reading, structural alignment, and numerical comparison; GUI Grounding emphasizes local inspection and coordinate precision; Visual Search emphasizes active evidence search in complex scenes; and Web-to-HTML emphasizes a generate-render-observe-revise loop. All domains share a unified visual toolset, so the model learns reusable operations such as cropping, marking, color analysis, structure detection, rendering, and final action expression rather than a separate interface for each task.

The OpenVisTool pipeline operationalizes the two data-quality questions. We first collect multi-domain visual tasks and filter out candidates that a base model can solve reliably without tools, keeping examples where external visual evidence has room to help. We then roll out a strong teacher model with the unified toolset and record the complete trajectory, including thinking, tool calls, tool outputs, and final responses. Next, we check final-result correctness using domain-appropriate evaluators, such as rule-based matching for structured outputs, judge models for open answers, point-in-box checks for GUI grounding, and render-based visual judging for Web-to-HTML. Finally, we apply \toolgain filtering: the teacher's tool observations are given to a base model, and the trajectory is retained only when those observations improve the model's ability to solve the query. The main dataset is the intersection of correctness-passing and tool-gainful trajectories.

This design also yields controlled variants for analysis. A correctness-only variant tests whether final-answer filtering is sufficient; a tool-gain-only variant tests whether useful observations are enough without enforcing reliable final trajectories; and a no-tool trajectory variant compares tool-use supervision against pure text-reasoning supervision on the same queries. These variants let us separate the effect of task selection, final-answer quality, tool-output usefulness, and the trajectory format itself.

Our experiments show that the resulting data improves visual tool use across model scales and families. Fine-tuning on \dataset improves all five domains for Qwen3.5-4B, Qwen3.5-9B, Qwen3.5-27B, and Qwen3-VL-8B-Instruct. On Qwen3.5-9B, average accuracy rises from 32.6 to 45.8, with large gains on Visual Search (+23.8) and Table (+17.3). The filtering ablation confirms that correctness and \toolgain are complementary: the intersection corpus outperforms both correctness-only and tool-gain-only variants on every domain. Compared with no-tool trajectory SFT, \dataset is stronger on four of five domains and by 8.7 average points, indicating that tool-use supervision is most valuable when tools reveal evidence unavailable from the original input.

At the same time, our results identify an important boundary case. GUI Grounding benefits from OpenVisTool relative to the raw no-tool baseline, but no-tool trajectory SFT performs better under the current point-in-box evaluation. We treat this as a diagnostic result rather than hide it: for tasks whose final output is a single coordinate, direct imitation can be more sample-efficient than a multi-step tool protocol with cropping, coordinate remapping, and action-format decisions. This suggests that visual tool-use distillation is not a uniform replacement for all forms of supervision; its strongest advantage appears in tasks where tools acquire new visual evidence.

In summary, our contributions are:
\begin{itemize}
  \item We present \method, an open pipeline for synthesizing multi-domain visual tool-use trajectories under a shared visual toolset.
  \item We construct \dataset, a 42K-example corpus covering Chart, GUI Grounding, Table, Visual Search, and Web-to-HTML, chosen for complementary visual bottlenecks and tool demands.
  \item We propose double rejection sampling based on task difficulty, final-answer correctness, and \toolgain, retaining trajectories that both solve the task and contain tool observations that improve solvability.
  \item We provide controlled dataset variants and experiments showing that correctness and \toolgain filters are complementary, that tool-use trajectories outperform no-tool trajectories on evidence-acquisition domains, and that GUI Grounding exposes a useful limitation of the current action protocol.
\end{itemize}
